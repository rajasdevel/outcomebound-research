# Gemma 4 E4B (instruction-tuned)

Gemma 4 E4B is the larger edge model of the Gemma 4 generation (class Gemma, generation 4): 4.5 billion effective parameters (8 billion with per-layer embeddings), 42 layers, a 128K window, open weights under Apache 2.0, taking text, image, video and audio and returning text. Google released it on 2026-04-02 for phones, laptops and small boards (its launch post names phones, Raspberry Pi and NVIDIA Jetson Orin Nano, and says the edge models run fully offline). Its predecessor in the edge line is Gemma 3n E4B. Google publishes one prompting and formatting guide for all Gemma 4 sizes; this file states what differs for the E4B and links to the [31B file](gemma-4-31b-it.md), which holds the family-wide rules.

## How to instruct it

Family-wide guidance, with the size table, is in [gemma-4-31b-it.md](gemma-4-31b-it.md). Differences for this model follow.

### Setting up the prompt

- Same system, user and model roles, turn markers and think token [gemma-prompt-formatting-4] (L). Instruction following (thinking mode, maker): IFEval 96.7, IFBench 44.0, well below the 31B's 76.0 on IFBench [gemma-4-tech-report] (L). Google's model card says the family does best on clearly framed tasks [gemma-model-card-4] (L); for the E4B, the gap to the larger sizes in Google's tables is widest on IFBench, Tau2 telecom and the agentic and contest-coding rows (see Benchmarks).

### Reasoning and effort

- Same on or off switch and no levels. Unlike the 12B, 26B A4B and 31B, the E2B and E4B templates do not insert an empty thought channel when thinking is off, and the model card says only the larger models write an empty thought block in that case [gemma-thinking, gemma-model-card-4] (L). A parser written for the larger sizes' empty block should still accept its absence.
- Google's LOW-thinking system instruction (about 20% fewer thinking tokens) and the history-stripping rule apply [gemma-prompt-formatting-4] (L).
- Practitioner test (A): on a Japanese commonsense set run through Ollama, thinking lowered accuracy at every Gemma 4 size by 1.2 to 9.2 points; the E4B scored 93.5% without thinking [classmethod-dgx-spark].

### Output: format, length, tone

- No verbosity, prefill or tone controls are published. For speech input Google gives exact transcription and translation prompts (transcription only, digits as digits) [gemma-prompt-formatting-4, gemma-audio] (L).

### Tools and agents

- Same native tool tokens and history rule as the 31B [gemma-function-calling-4] (L). Tau2 (thinking mode, maker): airline 52.0, retail 67.1, telecom 18.4 in the technical report. The model card's single average is 42.2, but the three report rows average 45.8; no source explains the difference [gemma-model-card-4, gemma-4-tech-report] (L). Terminal Bench Hard (harness not stated) is 8.0, against 36.0 for the 31B.
- Runtime bug and prompt fix (A): an Ollama issue opened 2026-04-13 against version 0.20.6 and gemma4:e4b reported that the tool-call parser failed when a system prompt, thinking off and tools were all present; the call appeared as raw text in the content field. Leaving thinking on made tool calls work but added 10 seconds or more of latency and leaked reasoning into streamed replies. An Ollama maintainer traced it to the runtime sending the empty thought block meant only for the two largest sizes, and 0.20.7-rc1 fixed the leak; the issue was closed on 2026-04-14. After the fix, the E4B with thinking off asked clarifying questions instead of calling the tool, and a project maintainer replied in the issue that small models often call tools better with reasoning on. The reporter then got immediate tool calls with thinking off by putting explicit rules with good and bad examples at the top of the system prompt [gh-ollama-15539].

### Coding

- LiveCodeBench v6 52.0, Codeforces Elo 940, SciCode 24.0 (thinking mode, maker) [gemma-4-tech-report] (L). No repository-level agent result from Google, and no independent result: no row on Scale's SWE-Bench Pro V2 (page dated 2026-09-22), no readable Terminal-Bench 4.0 row, no METR horizon [scale-swe-pro-v2, tbench-leaderboard, metr-time-horizons] (M).

### Long context and retrieval

- Window 128K (131,072 tokens); sliding window 512. In Google's long-context table, run without thinking: RULER 95.2 at 32k and 86.6 at 128k; LOFT 128k recall 58.5; GraphWalks F1 50.9; MTOB (English to Kalamang) 37.8 and (reverse) 34.6 at about 128k. There are no 256k rows for this size. MRCR v2 8-needle at 128k is 25.4 in the main table, in thinking mode [gemma-4-tech-report] (L). Google says the E4B outperforms Gemma 3 27B on long context; the table supports that on RULER (86.6 against 66.0 at 128k), LOFT (58.5 against 8.6), GraphWalks (50.9 against 32.8) and Kalamang to English (34.6 against 31.2), but not on English to Kalamang (37.8 against 41.0).
- Memory: the report gives 9.0 GB bf16, 2.3 GB with Google's mobile quantization and 0.14 GB for an int8 KV cache at 32k tokens, text only, and lists KV-cache sharing at a ratio of 18 to 42 for this size [gemma-4-tech-report] (L). Google's overview page gives 17.9 GB (BF16), 8.9 GB (SFP8), 4.5 GB (Q4_0), 2.5 GB (mobile) and 2.2 GB (mobile, text only) to load the weights, with 20% overhead and no KV cache; the larger figures include the per-layer embedding tables, which the page says are large but used only for lookups [gemma-core-docs] (L). Ollama lists the E4B download at 6.6 to 9.5 GB and uses it as the default gemma4 tag [ollama-gemma4] (A).

### Structured output

- Family position: the launch post claims structured JSON output; no schema mode is documented [gemma-4-blog] (L). One practitioner's ten-image tagging test parsed as JSON every time on the E4B [classmethod-dgx-spark] (A).

### Images, audio, other inputs

- Images: 150M vision encoder; token budgets 70 to 1120; image before text. At 1120 tokens: MMMU Pro 52.6, MATH-Vision 59.5, InfographicVQA 70.0, OmniDocBench 1.5 distance 0.181; at 280 tokens: 51.4, 59.2, 54.8 and 0.307. Google says the E4B equals or beats Gemma 3 27B on every vision evaluation; its own table shows one exception, InfographicVQA at 70.0 against 70.6 [gemma-4-tech-report] (L).
- Audio: 305M encoder; up to 30 seconds, mono 16 kHz, 25 tokens per second; the model card places audio after the text of the prompt. The technical report gives averages of 0.075 FLEURS word or character error over 12 languages and 38.2 CoVoST BLEU into English over seven source languages; Arabic has the highest error (0.162) [gemma-audio, gemma-4-tech-report] (L). The model card lists different single values for the E4B, CoVoST 35.54 and FLEURS 0.08, and neither source explains the gap [gemma-model-card-4] (L).
- Video: up to about 60 seconds at one frame per second [gemma-model-card-4] (L).

### Sampling and API parameters

- Temperature 1.0, top_p 0.95, top_k 64 [gemma-model-card-4] (L). The Gemini API model list read names only the 31B and 26B A4B; Google's pricing page shows Gemma 4 as free tier only. No output limit is published [gemma-on-gemini-api, gemini-pricing] (L).

### Migrating from the previous generation

- From Gemma 3n E4B (the earlier edge model) or Gemma 3: the 31B file lists the generation changes. For the edge line, Google reports that the audio encoder shrank from 680M to 305M parameters and from 390 MB to 87 MB on disk, yet translation improved by 10% and transcription by 12% in relative terms for the E4B (E4B CoVoST 38.2 against 34.7 for Gemma 3n E4B; FLEURS 0.075 against 0.085). Audio now costs 25 tokens per second against 6.25 for Gemma 3n [gemma-4-tech-report, gemma-audio] (L).

## What the system card reports

Google's model card and technical report cover all sizes together [gemma-model-card-4, gemma-4-tech-report] (L). The safety text is the same as for the 31B: five policy areas, filtered data, no-filter safety testing showing improvement over Gemma 3 and 3n and low unjustified refusals, and no published refusal rates, red-team, chemical, biological, radiological, nuclear, cyber, prompt-injection, sycophancy, reward-hacking or deception results (details in the [31B file](gemma-4-31b-it.md)). The report gives no Arena Text entry for this size, and none was found on the live board.

## Behaviour observed in practice

- On a DGX Spark with Ollama (BF16), the E4B answered a Japanese commonsense question in 0.28 s on average and scored 93.5%, falling to 92.3% with thinking on, which made it about 7.5 times slower (A, one setup) [classmethod-dgx-spark].
- Tool calls with thinking off (A): after a runtime fix, the model still tended to ask clarifying questions instead of calling a tool until the system prompt gave explicit rules and examples; with thinking on, calls worked (see Tools and agents) [gh-ollama-15539].
- Artificial Analysis measured 60.9 output tokens per second and 1.06 s to first token, and shows a median hosted price of $0.02 input and $0.10 output per Mtok from a single provider (M) [aa-gemma-4-e4b].

## Open questions

- Which Tau2 average for the E4B is right (42.2 on the model card, 45.8 from the report's rows).
- How reliably the E4B calls tools with thinking off across runtimes; the one documented case needed a more explicit system prompt after the runtime fix.
- Which audio averages are right (the report's 38.2 and 0.075, or the model card's 35.54 and 0.08).
- How the E4B performs on agentic and repository-level tasks; no source reports one.
- A full Artificial Analysis evaluation, since its score is an estimate.
