# Gemma 4 31B (instruction-tuned)

Gemma 4 31B is the largest model of the Gemma 4 generation (class Gemma, generation 4) and its only dense model without audio input: 30.7 billion parameters, 60 layers, open weights under Apache 2.0, text, image and video in, text out. Google released it on 2026-04-02 together with E2B, E4B and 26B A4B (a 12B followed on 2026-06-03). It replaced Gemma 3 27B, the top size of the previous generation, which had a 128K window, text and image input, no thinking mode and no system role. Google publishes one prompt-formatting guide and a set of capability pages for the whole family, so this file carries the family-wide rules and the other four Gemma 4 files link here and state only what differs.

## How to instruct it

Family-wide facts that hold for all five Gemma 4 sizes (the other files do not repeat them). Numbers are from Google's model card and technical report [gemma-model-card-4, gemma-4-tech-report] (L).

| Size | Parameters | Layers | Context | Sliding window | Input | Vision / audio front end |
| --- | --- | --- | --- | --- | --- | --- |
| E2B | 2.3B effective, 5.1B with per-layer embeddings | 35 | 128K | 512 | text, image, video, audio | 150M vision encoder, 305M audio encoder |
| E4B | 4.5B effective, 8B with per-layer embeddings | 42 | 128K | 512 | text, image, video, audio | 150M vision encoder, 305M audio encoder |
| 12B Unified | 11.95B | 48 | 256K | 1024 | text, image, video, audio | no encoders: image patches and audio chunks are projected straight into the language model |
| 26B A4B | 25.2B total, 3.8B active (8 of 128 experts plus one shared) | 30 | 256K | 1024 | text, image, video | 550M vision encoder |
| 31B | 30.7B | 60 | 256K | 1024 | text, image, video | 550M vision encoder |

All sizes share a 262K-token vocabulary, a pre-training data cutoff of January 2025, pre-training on more than 140 languages (the model card claims ready-to-use support for more than 35), and Apache 2.0 licensing. Attention mixes local sliding-window layers with global layers (5 local to 1 global, 4 to 1 on E2B). Google also ships multi-token-prediction (MTP) drafter checkpoints for speculative decoding. Its blog post is dated 2026-05-05 and claims up to 3x faster decoding with output identical to plain decoding; its releases page lists the drafters on 2026-04-16 [gemma-releases, gemma-mtp-blog] (L). Its MTP page says the drafter shares the target model's input embeddings and last-layer activations, and that the 26B A4B may gain little at batch size 1 because checking drafted tokens can need extra expert weights; the blog gives about 2.2x for the 26B A4B on Apple silicon at batch sizes 4 to 8 [gemma-mtp, gemma-mtp-blog] (L). Quantization-aware-trained (QAT) checkpoints followed on 2026-06-05, per Google's blog; the releases page does not list them [gemma-qat-blog, gemma-releases] (L).

Google's overview page gives approximate memory to load the weights alone, with 20% overhead and no KV cache: E2B 11.4 GB (BF16), 5.7 GB (SFP8), 2.9 GB (Q4_0), 1.1 GB (mobile), 0.84 GB (mobile, text only); E4B 17.9, 8.9, 4.5, 2.5 and 2.2 GB; 12B 26.7, 13.4 and 6.7 GB; 26B A4B 57.7, 28.8 and 14.4 GB; 31B 69.9, 34.9 and 17.5 GB. The same page maps QAT downloads to runtimes: GGUF for llama.cpp and LM Studio, compressed-tensors (w4a16) for vLLM and SGLang (not offered for the 26B A4B), unquantized QAT weights plus a matching "assistant" drafter for speculative decoding, and mobile formats for E2B and E4B only [gemma-core-docs] (L). The technical report gives different, text-only footprints (for example 64.0 GB bf16 and 19.2 GB Q4_0 for the 31B); neither source reconciles the two sets [gemma-4-tech-report] (L).

Where Google's guidance lives: the prompt-formatting page (control tokens, thinking, tool calls, thought handling), a thinking page, a function-calling page, image, video and audio pages, and a page on calling the 26B A4B and 31B through the Gemini API [gemma-prompt-formatting-4, gemma-thinking, gemma-function-calling-4, gemma-vision-image, gemma-vision-video, gemma-audio, gemma-on-gemini-api] (L). None of them is a guide to prompt style in the sense of role prompts, XML versus Markdown, or example selection; they document the format the model was trained on.

### Setting up the prompt

- The Gemma 4 chat format has three roles, system, user and model, each opened by a turn marker and closed by an end-of-turn marker. Google's example shows a system turn holding the instruction text [gemma-prompt-formatting-4] (L). This differs from Gemma 3, whose instruction-tuned models took only user and model roles, with system-level text placed in the first user message [gemma-3-prompt-structure] (L).
- The technical report says to add the beginning-of-sequence token explicitly after tokenization (or use the tokenizer's add_bos option) and not to tokenize the literal text "[BOS]". Instruction-tuned models end a reply with the end-of-turn marker, where pre-trained models end with the end-of-sequence token, so fine-tuning data needs the matching end token [gemma-4-tech-report] (L).
- In practice the chat template of the serving stack builds all of this. Google lists the control tokens so that a parser, a template or a fine-tuning set can match them. Its pages name the roles differently: the format page uses system, user and model tokens, while its JSON chat-history examples and the model card use the system, user and assistant roles that chat templates expect [gemma-prompt-formatting-4, gemma-model-card-4] (L).
- The format page says thinking is set for the whole conversation and belongs in one system turn together with the other system instructions, including tool declarations [gemma-prompt-formatting-4] (L).
- Google gives no Gemma-specific advice on role prompts, tag structure, few-shot examples or where to put long documents in a text prompt. The model card says only that the models do best on clearly framed tasks and are weaker on open-ended, highly complex ones, and on nuance, sarcasm and figurative language [gemma-model-card-4] (L).
- Instruction following as Google measures it (thinking mode): IFEval 98.9 and IFBench 76.0 for the 31B [gemma-4-tech-report] (L, maker).
- System instructions can shape the thinking itself. Google says a system instruction asking for LOW thinking cuts thinking tokens by about 20%, and that there is no single best prompt for this; it gives no wording [gemma-prompt-formatting-4] (L).

### Reasoning and effort

- Thinking is a switch, not a scale. Putting the think token at the start of the system turn turns it on; leaving it out turns it off. With it on, the model writes its reasoning inside a thought channel (opened by a channel marker followed by the word thought, closed by a channel-close marker) and then the answer [gemma-prompt-formatting-4, gemma-4-tech-report] (L).
- In Hugging Face Transformers (the capability pages install version 5.10.1 or later) the switch is enable_thinking in apply_chat_template, and parse_response returns separate thinking, content and tool_calls fields; the page says decoding must keep special tokens for that parser to work [gemma-thinking] (L). Through the Gemini API the switch is thinking_level, "high" to think and "minimal" to turn thinking off; Google says Gemma 4 supports only on or off there [gemma-on-gemini-api] (L).
- There is no effort level, no token budget and no interleaved-thinking setting in the pages read. The only published lever on depth is the system-instruction wording described above.
- When thinking is off, the 12B, 26B A4B and 31B templates insert an empty thought channel; E2B and E4B do not [gemma-thinking, gemma-model-card-4] (L). Google adds that the 26B A4B and 31B may occasionally still write a thought channel with thinking off, and that adding the empty thought channel to the prompt makes them steadier. For fine-tuning those two on data with no thinking, it recommends the empty channel in the training prompts [gemma-prompt-formatting-4] (L). A parser therefore has to accept an empty or an unexpected thought block.
- History rule: Google's pages say the thoughts of earlier model turns are removed before the conversation is sent back. The exception is a turn that contains tool calls, where the thoughts stay until the tool sequence ends. Thinking can be switched off mid-conversation by dropping the think token at the same time as the old thoughts. For long-running agents Google suggests summarising the earlier thoughts into ordinary text and feeding that back, because dropping all reasoning context can let the model fall into cyclical reasoning loops [gemma-prompt-formatting-4, gemma-thinking] (L).
- Whether thinking helps depends on the task. Google reports most of its headline results in thinking mode and the long-context table without it [gemma-4-tech-report] (L). Two outside observations point the other way for some tasks: on a multi-turn image-grounding game, the 31B with thinking scored lower than without it, and a practitioner's Japanese commonsense test lost accuracy with thinking at every size (see Behaviour observed in practice) [arxiv-amigo, classmethod-dgx-spark] (M, A).
- Google gives no guidance on "think step by step" prompting for a model with thinking on.

### Output: format, length, tone

- Google publishes no verbosity, length or tone controls and no prefill guidance for Gemma 4. The format page notes that the thought channel is normally hidden from end users and that tool tokens mediate the exchange between application and model [gemma-prompt-formatting-4] (L).
- The instruction-tuned model ends its reply with the end-of-turn marker, where the pre-trained model ends with the end-of-sequence token; the technical report says fine-tuning data must use the end token that matches the model type [gemma-4-tech-report] (L). The format page adds that the token opening a tool response acts as an extra stop sequence, so generation halts when the model has written a tool call [gemma-prompt-formatting-4] (L).
- For speech input, Google gives exact wording for transcription (output only the transcription, write digits as digits) and translation prompts, and says a plain request to transcribe the audio also works; the 31B has no audio input, so these apply to E2B, E4B and 12B [gemma-prompt-formatting-4] (L).

### Tools and agents

- Function calling is built in. A tool is declared in the system turn with a declaration block; the model replies with a call block (function name, then its arguments), and the application returns a response block. A single string-delimiter token wraps every string value so that braces, commas and quotes inside a value are literal [gemma-prompt-formatting-4, gemma-4-tech-report] (L).
- The function-calling page sums up a four-stage cycle: define tools, the model returns a call, the application parses and runs it and appends the result, the model writes the final answer. It stresses that a Gemma model cannot run code itself, that function names and arguments must be validated before execution, and that looking up functions dynamically with globals() can be dangerous in production [gemma-function-calling-4] (L).
- Tools can be given as hand-written JSON schemas or as Python functions whose type hints and docstrings become the schema; Google advises Google-style docstrings and prefers hand-written schemas for nested parameters. Results go back as a tool_responses list of name and response pairs so the template builds the right tokens [gemma-function-calling-4] (L).
- Thinking and tools combine: the page shows enable_thinking with function calling and says it gives more precise decisions about when to call a tool, while the history rule keeps thoughts through the tool sequence [gemma-function-calling-4] (L).
- Several calls in one turn: the function-calling page shows the tool_responses list holding results for multiple independent requests, and its example parser collects every call block in a reply, but it does not discuss parallel calling as such. The pages read say nothing on forcing or forbidding a call (tool choice) or on recovery from failed calls [gemma-function-calling-4] (L).
- Through the Gemini API, the Gemma page shows function declarations and a Google Search tool for Gemma 4 [gemma-on-gemini-api] (L), while Google's pricing page lists grounding with Google Search as not available for Gemma 4 in either tier [gemini-pricing] (L). The two pages disagree, and neither says which applies.
- Tool-use scores (thinking mode, maker): Tau2 airline 75.0, retail 86.4, telecom 69.3 for the 31B (average 76.9), against 39.0, 6.6 and 3.1 for Gemma 3 27B [gemma-4-tech-report] (L). Google's own text does not say which Tau2 harness or user simulator it used.
- Serving stacks have had bugs in the tool and thought parsers. In one Ollama case (fixed in April 2026) a maintainer traced a tool-call failure on the E4B to the runtime sending the empty thought block that is meant only for the two largest sizes (see the E4B file) [gh-ollama-15539] (A). Results therefore depend on the runtime's template and parser version as well as on the prompt.

### Coding

- Google's coding numbers for the 31B are LiveCodeBench v6 80.0, Codeforces Elo 2150, SciCode 43.0 and a row called Terminal Bench Hard at 36.0 (thinking mode, maker), against 29.1, 110, 21.0 and 4.0 for Gemma 3 27B [gemma-model-card-4, gemma-4-tech-report] (L). The report does not name the harness, version or tool setup behind the Terminal Bench Hard row.
- Google reports no SWE-Bench-style repository task result and publishes no coding-agent harness advice for Gemma 4. The launch post describes native function calling and system instructions as aimed at autonomous agents [gemma-4-blog] (L).
- No independent coding-agent measurement was found: the 31B has no row on Scale's SWE-Bench Pro V2 leaderboard (page dated 2026-09-22), no readable row on the Terminal-Bench 4.0 leaderboard, and no METR time horizon [scale-swe-pro-v2, tbench-leaderboard, metr-time-horizons] (M).

### Long context and retrieval

- The window is 262,144 tokens (256K) [gemma-model-card-4] (L). Google's long-context table (Table 9) was run without thinking: RULER 96.8 at 32k and 96.4 at 128k; LOFT text retrieval recall 79.5 at 128k; GraphWalks F1 82.3 below 128k; MTOB translation chrF 52.9 (English to Kalamang) and 48.6 (reverse) at about 128k, and 54.3 and 46.2 at about 256k. Gemma 3 27B scored 66.0 on RULER 128k and 8.6 on LOFT 128k in the same table. Separately, MRCR v2 8-needle at 128k is 66.4 in the main table (Table 5), where Gemma 4 results are in thinking mode [gemma-4-tech-report] (L).
- Google's model card notes that output quality generally rises with more context only up to a point; it gives no figure for where that point is [gemma-model-card-4] (L).
- The 31B holds up better at 128k than the smaller Gemma 4 sizes on every long-context row (the 26B A4B scores 89.8 on RULER 128k and 44.1 on MRCR). No document-placement or query-position advice is published for text.
- Memory: the report gives 64.0 GB for bf16 weights, 19.2 GB for the Q4_0 quantized checkpoint, and 1.10 GB more for an int8 KV cache at 32k tokens. Global-layer KV cache is up to 37.5% smaller through key-as-value reuse and p-RoPE [gemma-4-tech-report] (L). The 31B has the largest KV cost of the family at a given length.
- No prompt-caching feature is documented for the open weights; Google lists context caching as free in the Gemini API free tier only [gemini-pricing] (L).
- Reports of slow long-context serving exist: a vLLM issue (opened 2026-08-12, open when read) says plain decoding on the 31B was three or more times faster than multi-token-prediction decoding above roughly 50k tokens on four RTX 3090 cards, while llama.cpp did not show it. Later comments trace it to vLLM forcing a Triton attention backend for Gemma 4 on that GPU generation; the reporter found that choosing the FlashInfer backend restored MTP speed at long context, and fixes were still open pull requests when read [gh-vllm-52049] (A).

### Structured output

- Google's launch post lists native structured JSON output and function calling [gemma-4-blog] (L). The Gemma pages read describe no JSON-schema mode or constrained-decoding switch, and the Gemini-API page for Gemma does not mention structured output [gemma-on-gemini-api] (L). Schema enforcement therefore depends on the runtime (for example a grammar feature in the server), not on a documented model setting.
- One practitioner's test asked every Gemma 4 size to turn ten photos into JSON tags; all of them produced parseable JSON every time (ten images is a small sample) [classmethod-dgx-spark] (A).

### Images, audio, other inputs

- Images: variable aspect ratio and resolution. Each image gets a token budget of 70, 140, 280, 560 or 1120. Google says lower budgets suit classification, captioning and video, and higher budgets suit OCR, document parsing and small text; the image page shows a 70-token budget missing details that a 560-token budget caught [gemma-model-card-4, gemma-vision-image] (L). In Transformers the budget is the image processor's max_soft_tokens.
- The 31B's own numbers show why: at 1120 tokens, MMMU Pro 76.9, MATH-Vision 85.6, InfographicVQA 92.0 and OmniDocBench 1.5 edit distance 0.131 (lower is better); at 280 tokens, 75.8, 83.4, 82.8 and 0.201 [gemma-4-tech-report] (L). Reasoning-style vision tasks lose little at 280; infographics and document parsing lose more.
- Order: the model card's best practice places image content before the text of the prompt [gemma-model-card-4] (L). Several images can go in one prompt. For detection the page shows a prompt such as "detect person and car" that also asks for JSON only, returning box_2d as [y1, x1, y2, x2] on a 0 to 1000 grid, to be rescaled to the image size [gemma-vision-image] (L). The model card lists OCR (including multilingual), document and PDF parsing, screen and UI understanding, charts, handwriting and pointing among the image tasks, and says text and images can be interleaved in any order, although its stated best practice is image first [gemma-model-card-4] (L).
- Video: input is processed as frames, up to 60 seconds assuming one frame per second, per the model card. The video page documents only how to pass a video URL through the processor; its example prompt shows a timestamp before each frame, and it gives no frame-rate or per-frame token settings [gemma-model-card-4, gemma-vision-video] (L).
- Audio: not supported by the 31B (E2B, E4B and 12B take audio). Output is text only.

### Sampling and API parameters

- Google gives one standard setting for all uses: temperature 1.0, top_p 0.95, top_k 64 [gemma-model-card-4] (L). Nothing in the pages read says whether the Gemini API accepts or ignores these for Gemma.
- Through the Gemini API the model ids are gemma-4-31b-it and gemma-4-26b-a4b-it (added 2026-04-02), with system instructions, function calling, thinking_level, image input, multi-turn chat and Google Search grounding listed. Google's pricing page shows the free tier only and no paid tier, with free-tier content used to improve its products; tuning is not offered [gemma-on-gemini-api, gemini-api-changelog, gemini-pricing] (L). Google's Gemini API rate-limits page has no Gemma rows, so the free-tier limits are not published there [gemini-rate-limits] (L).
- Google publishes no maximum output length for Gemma 4 in the pages read.

### Migrating from the previous generation

Gemma 3 27B to Gemma 4 31B, as the sources show [gemma-3-prompt-structure, gemma-3-model-card, gemma-prompt-formatting-4, gemma-4-tech-report] (L):

- Chat format: Gemma 3 used start-of-turn and end-of-turn markers with only user and model roles; Gemma 4 uses turn markers with system, user and model roles and a different end marker. A template or stop-token list written for Gemma 3 does not carry over.
- System prompt: Gemma 3 had no system role (instructions went into the first user turn); Gemma 4 has one.
- Thinking: new in Gemma 4 (the think token, the thought channel and the history-stripping rule). Gemma 3 had none.
- Tools: Gemma 4 has dedicated declaration, call and response tokens and a string delimiter; the Gemma 3 pages read describe none. Tau2 retail rose from 6.6 to 86.4.
- Context: 128K for Gemma 3 27B, 256K for the 31B. Long-context scores rose sharply (LOFT 128k from 8.6 to 79.5).
- Images: Gemma 3 normalized images to 896 by 896 and used 256 tokens each (Google's Gemma 3 vision tests in the Gemma 4 report used Pan & Scan); Gemma 4 keeps the aspect ratio with a 70 to 1120 token budget. Video input is new in Gemma 4.
- Knowledge cutoff: January 2025 for Gemma 4 and August 2024 for Gemma 3.
- Sampling: the Gemma 4 model card gives one standard setting (temperature 1.0, top_p 0.95, top_k 64); the Gemma 3 pages read give no sampling recommendation.
- Licence: Gemma 4 is under Apache 2.0, where the Gemma 3 model card points to Google's own Gemma terms of use [gemma-4-blog, gemma-3-model-card] (L).

## What the system card reports

Google publishes a model card and the Gemma 4 technical report (arXiv 2607.02770, revised 2026-07-24); it does not publish a separate document called a system card, and the safety section of these two is short [gemma-model-card-4, gemma-4-tech-report] (L).

- Capabilities measured: the benchmark tables in this file (reasoning, maths, code, instruction following, tool use, vision, long context), and human preference on Arena Text, where the 31B scored 1451 (interval 8, rank 43) as of 2026-06-19 and Google calls it the top dense open model on that board.
- Process: Google says Gemma 4 went through the same safety evaluations as its Gemini models, built with internal safety and responsible-AI teams, using automated and human evaluations [gemma-model-card-4, gemma-4-tech-report] (L).
- Safety policy areas: child sexual abuse material and exploitation; dangerous content such as promoting suicide or instructing real-world harm; sexually explicit content; hate speech; harassment that encourages violence. CSAM filtering was applied at several stages of data preparation, automated filters took some personal and other sensitive data out of the training sets, and the post-training sets were cleaned of unsafe or toxic outputs, wrong self-identification and duplicates. Google also added post-training examples of in-context attribution, hedging and refusal to cut hallucination, and reports better factuality scores with no loss elsewhere.
- Results: Google says every content-safety category improved over earlier Gemma models, that unjustified refusals stay low, and that text-to-text and image-to-text tests across all sizes showed minimal policy violations. All safety testing was done with no safety filters in front of the model.
- Not reported: refusal or over-refusal rates, red-team methods and results, chemical, biological, radiological, nuclear or cyber evaluations, prompt-injection results, sycophancy, reward-hacking or test special-casing, deception or sandbagging, and memorization measurements. The report refers to Google DeepMind's Frontier Safety Framework but gives no framework results.
- Deployment safeguards: the weights are open, so no hosted classifier stops a request by default. Google says safe use takes a system-level approach, points to its Responsible Generative AI Toolkit, and asks developers to set their own content-safety configuration, monitor for bias and follow local privacy rules. It lists limits: weaker on open-ended complex tasks, nuance and common-sense reasoning, and answers come from patterns in training data, so facts may be wrong.

## Behaviour observed in practice

- Thinking on versus off, image grounding (M, [arxiv-amigo]): an independent benchmark (AMIGO, arXiv 2603.28662, revised 2026-09-16) ran Gemma 4 31B in a 20-question game to find a hidden image in a gallery. In the main runs thinking was off for the Gemma models because the authors found Gemma 4 thinking too slow (one other model kept its default thinking). In a separate run at similarity threshold 0.8, thinking lowered verified-correct accuracy from 9.8% to 7.5% and unverified accuracy from 25.0% to 22.4%, raised average rounds from 6.85 to 7.8, introduced premature outputs, and lowered recovery from 54.5% to 50.0%. With thinking off, the 31B had verified-correct accuracy of 25.2 to 27.9% at the lowest three thresholds, ran out of its question budget in only 2.7 to 7.0% of runs, had the lowest invalid-question rate of the five models (9.6 to 13.0%) and the highest recovery from a corrupted answer (59.1% macro average).
- Thinking on commonsense (A, [classmethod-dgx-spark]): one practitioner on a 128 GB DGX Spark with Ollama (2026-04-03) found thinking lowered accuracy on a 1,119-question Japanese commonsense set (3-shot) at every size, by 1.2 to 9.2 points, and measured the 31B at 97.9% without it; the 31B's thinking figure (92.4%) covers only 370 of the questions. Output was 4.6 tokens per second for the 31B in BF16, which used 117 GB of the 128 GB.
- Serving bugs (A): a vLLM issue reports the 31B MTP slowdown above about 50k tokens and a backend workaround [gh-vllm-52049]. A separate Ollama issue about the E4B shows tool calls lost when a system prompt, thinking off and tools are combined (see the E4B file) [gh-ollama-15539]. Both are specific to one runtime and version.
- Hosted speed: Artificial Analysis measured 35.4 output tokens per second and 1.12 s to first token through Google's API, and the model wrote 49M tokens during the index run [aa-gemma-4-31b] (M).

## Open questions

- Which harness, benchmark version and tool setup produced the Terminal Bench Hard row, and how the model does on repository-level agent tasks (no SWE-Bench-style or independent agent result exists).
- Whether Gemma 4 sampling settings apply through the Gemini API, and what the maximum output length is anywhere.
- Whether thinking helps or hurts for a given task: Google's tables favour it, two outside tests found cases where it did not.
- How the model behaves on safety dimensions the report does not quantify (over-refusal rates, prompt injection, cyber and biology uplift).
- Whether parallel tool calls and tool-choice constraints are supported; Google's pages are silent.
- Which structured-output method is dependable, since no documented schema mode exists.
- Whether Google Search grounding works for Gemma 4 in the Gemini API (the Gemma page shows it; the pricing page lists it as not available), and what the free-tier rate limits are.
