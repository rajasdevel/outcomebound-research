# Muse Glimmer 30B

Muse Glimmer 30B is an open-weight model from Meta (Apache-2.0), a dense transformer of about 29.6 billion parameters
including a perception encoder of about 1.8 billion, released on 2026-08-10. It is distilled from Muse Spark and built
for agents that run locally on a single consumer GPU or a Mac: tool use, long tasks and recovery from failed calls. It is the only model in its class and
has no earlier generation. Unlike [Muse Spark](muse-spark-1.3.md), Meta's API does not serve it, so every setting
below applies to self-hosted or third-party-hosted copies. Meta-wide context is on the [Meta page](README.md).

## How to instruct it

Meta publishes a prompting guide for this model, unlike Muse Spark. Most of it concerns formatting and serving, not
prompt wording, so the sections on wording say what Meta does not cover.

### Setting up the prompt

- **Use the chat template.** Meta's guide says to build prompts with the tokenizer's `apply_chat_template` and warns that
  formatting by hand degrades output. Without a system message the template inserts a short default one with a
  knowledge-cutoff line and the reasoning setting [meta-glimmer-prompting]. The template uses channel-style framing: `<|begin_of_text|>`, `<|start|>`, a role,
  `<|message|>`, the content and `<|eot|>` to end a turn; `<|eom|>` ends a message while the turn continues, and `<|image|>`
  marks image content. The guide says to pass `add_generation_prompt=True` when generating [meta-glimmer-prompting].
- **Roles.** system, user, assistant and tool. An assistant turn can carry a recipient: `to=user` for the normal reply,
  `to=self` for private reasoning and `to=<tool_name>` for a tool call [meta-glimmer-prompting].
- **System prompt.** It goes first, with the system role. Meta says effective ones are specific to the task, state their
  constraints up front and avoid instructions about the model's own internals [meta-glimmer-prompting]. Nothing is said
  about XML tags, Markdown, examples or where to put long documents.
- **Images.** The guide says to use `AutoProcessor`, not the bare tokenizer, and to give content as a list of image and text parts
  [meta-glimmer-prompting].
- **Deployment framing.** Meta recommends deploying the model inside a system with guardrails rather than as a bare
  endpoint, and human confirmation for irreversible actions in agentic use [hf-glimmer].

### Reasoning and effort

- **The control.** Reasoning strength has four levels: `low`, `medium`, `high` and `xhigh`. The model card says to write
  `Reasoning strength: <value>` in the system prompt. Meta's prompting guide calls the control the `reasoning_strength`
  parameter, with `high` as the default, and the llama.cpp recipe passes it as a chat-template argument
  (`--chat-template-kwargs '{"reasoning_strength":"low"}'`, per server or per request) [hf-glimmer,
  meta-glimmer-prompting, meta-glimmer-llamacpp].
- **Which level.** Meta advises `high` or `xhigh` for complex problem solving, coding and agent work [hf-glimmer]. The
  model card states no default, while the guide says `high`.
- **Thinking.** The model writes private chain of thought before answering, in an assistant turn addressed to itself;
  a prior trace can be replayed through the message's `reasoning_content` field. With vLLM, `--reasoning-parser
  muse_glimmer` places it in `message.reasoning`; with SGLang, `--reasoning-parser muse` and with llama.cpp the server
  default place it in `message.reasoning_content` [meta-glimmer-prompting, meta-glimmer-vllm, meta-glimmer-sglang,
  meta-glimmer-llamacpp].
- **It cannot be switched off.** Meta's llama.cpp page says the template always opens the thinking channel, so
  `reasoning_effort: "none"` changes nothing; llama.cpp ignores the OpenAI-style `reasoning_effort` altogether, and
  `--reasoning-budget N` is the way to cap thinking tokens there. The page adds that a lower level costs little where
  answers are checked or retries are cheap [meta-glimmer-llamacpp].
- **Budgets.** A `max_tokens` set too low truncates reasoning, which Meta lists as a common pitfall; under llama.cpp
  such a request returns empty content with `finish_reason: "length"`. Meta also advises streaming for
  reasoning-heavy requests, which can otherwise time out [meta-glimmer-prompting, meta-glimmer-vllm,
  meta-glimmer-llamacpp].
- **Cost.** At `high`, Artificial Analysis counted 59 million output tokens to run its index and about 14,000 output
  tokens a task (10,000 of them reasoning) [aa-glimmer, aa-compare-glimmer].

### Output: format, length, tone

- No verbosity, length or format control is documented.
- **Stopping.** The vLLM recipe says to stop on both token ids 200001 and 200008 and never on 200007, the end-of-message
  token. The SGLang recipe says never to stop on `<|eom|>` and that the end-of-text and `<|eot|>` ids belong in the
  checkpoint's `eos_token_id` metadata, not in a serve flag [meta-glimmer-vllm, meta-glimmer-sglang].
- Prefilling the assistant turn is not documented.

### Tools and agents

- **Format.** Tools go through the `tools` argument as OpenAI-style schemas; the model emits a call in an assistant
  turn addressed to the tool name, and the result returns as a `tool` message [meta-glimmer-prompting]. The Hugging Face
  blog says the processor's `apply_chat_template` takes `tools` and that multimodal tool calling works [hf-blog-glimmer].
- **Parsers.** vLLM needs `--enable-auto-tool-choice --tool-call-parser muse_glimmer` (underscore); SGLang uses
  `--tool-call-parser muse`. The parser name must match the runtime [meta-glimmer-vllm, meta-glimmer-sglang].
- **Parallel calls.** Meta's guide says the model makes one tool call per turn, with no parallel calls. The vLLM
  recipe warns that several calls arrive as consecutive messages and that reading only the first drops work. The two
  statements do not agree, so handle both shapes [meta-glimmer-prompting, meta-glimmer-vllm].
- **What Meta says it is built for.** Tool use with precise schemas, long tasks, and diagnosing and recovering from
  failed calls; the card says it works with agent harnesses such as OpenClaw and Hermes Agent [hf-glimmer]. Its tables give 75.5 on MCP
  Atlas (public) and 23.5 on tau3-Banking at `high`, ahead of the two open peers it compares with [hf-glimmer].
- **Long-horizon behaviour.** Meta's launch page describes persistent state across restarts and multi-hour sessions as
  a product aim; the model card gives no measurement [meta-glimmer-page].

### Coding

- Meta lists coding agents and local coding assistance as intended uses [hf-glimmer, meta-glimmer-post]. Its table (at
  `high`, temperature 1.0, top-p 0.95, top-k 64) gives SWE-Bench Pro 51.2 and SWE-Bench Verified 76.0, run by Meta with a
  scaffold of a bash tool and a file tool, averaged over four runs, on the original 731-task Pro set; and Terminal-Bench
  2.1 51.7 with the Terminus 2 harness, a figure Meta's methodology says it took from Artificial Analysis
  [hf-glimmer, meta-glimmer-methodology].
- Artificial Analysis's own Terminal-Bench 4.0 run resolved 1% of tasks [aa-compare-glimmer]. No Coding Agent Index
  score exists.
- Meta says the model works with agent scaffolds such as OpenClaw and Hermes Agent. The Hugging Face blog (written with
  Meta) positions it for privacy-aware coding, document analysis and personal assistants [hf-glimmer, hf-blog-glimmer].

### Long context and retrieval

- **Window.** The model card says 131,072 or more tokens; Meta's docs say 128K by default with longer contexts supported,
  and its llama.cpp page calls 131,072 the native context; the Hugging Face blog's 32,768 comes from an example agent
  configuration and is not stated as a limit [hf-glimmer, meta-glimmer-docs, meta-glimmer-prompting,
  meta-glimmer-llamacpp, hf-blog-glimmer].
- **Architecture.** Three of every four layers use a sliding window of 2,048 tokens and the fourth attends globally; the
  key-value heads are few (2 against 32 query heads), so the cache is small [hf-glimmer].
- **Measures.** AA-LCR 80.0 in Meta's table (83% on Artificial Analysis's own run) and Beam128K 65.1, ahead of Gemma4-31B
  and Qwen3.6-27B in Meta's comparison [hf-glimmer, aa-compare-glimmer].
- **Serving.** llama.cpp divides the context among parallel slots: `-c 131072 -np 1` gives 131,072 tokens to one slot, and
  `-c 524288 -np 4` gives each of four slots 131,072; with `-c 131072 -np 4` each slot gets 32,768, and Meta warns that a
  single reasoning generation can fill that and fail with no answer and no error [meta-glimmer-llamacpp]. vLLM's recipe
  asks for 72 GB of VRAM at full precision (about 60 GB of weights), while the model card's table targets 64 GB for full
  precision; the Hugging Face blog lists one 80 GB H100 as the practical minimum for BF16 inference
  [meta-glimmer-vllm, hf-glimmer, hf-blog-glimmer].

### Structured output

- Meta's pages describe no constrained-decoding or JSON-schema mode for this model. They describe schema-driven tool
  calls and, for image grounding, asking for JSON in the prompt; the runtimes' own structured-output features lie
  outside Meta's recipes. The Hugging Face blog includes a fine-tuning example that teaches the model a structured
  output format [hf-blog-glimmer].

### Images, audio, other inputs

- **Images.** A frozen ViT-G/14 perception encoder of about 1.8 billion parameters takes up to 4,096 visual tokens per
  image. llama.cpp needs the separate `--mmproj` projector file (about 1.4 GB) for images [hf-glimmer,
  meta-glimmer-llamacpp, meta-glimmer-quant].
- **Video.** Not optimised; processed as individual frames. The Hugging Face blog says 2 frames per second, capped at 96
  frames [hf-glimmer, hf-blog-glimmer].
- **Audio.** Not supported, as input or output [hf-glimmer].
- **Measures.** CharXiv Reasoning 78.8, ScreenSpot Pro 75.4, OmniDocBench v1.5 75.8, MMMU Pro 74 and OSWorld-Verified 65.9
  in Meta's table, with Qwen3.6-27B ahead on the last four [hf-glimmer].

### Sampling and API parameters

- Meta recommends temperature 1.0, top-p 0.95 and top-k 64 [hf-glimmer]. In vLLM, `--generation-config auto` applies them;
  the recipe warns that sending temperature 0 overrides the published settings and advises against it
  [meta-glimmer-vllm].
- Quantised builds: a Q4_K_M build of about 16.8 GB (fits a 24 GB card: 15.6 GiB of weights plus 1.3 GiB of projector and
  2.1 GiB of cache, 19.0 GiB in all) and a Q4_K_XL build of about 19.7 GB for 32 GB hardware. Meta says the 32 GB build loses
  about 0.2% and the 24 GB build about 1.0% on the average of 15 of its benchmarks [meta-glimmer-quant, hf-glimmer].
- DFlash speculative decoding (a 1.6 GB drafter, block size 16): Meta measured 74.9 to 233.4 tokens a second on an RTX 5090
  (3.1 times), 26.6 to 50.2 on an Apple M5 Max and 23.7 to 37.8 on an M4 Max, at batch size 1 with greedy decoding on the
  24 GB build [hf-glimmer].
- Transformers 5.15 or later gives native support [meta-glimmer-get].

### Migrating from the previous generation

There is no earlier Muse Glimmer. A prompt moved over from Muse Spark changes in these ways: the reasoning level is set in
the system prompt or template, not by an API field; tool calls follow the template's recipient format with the parser
flags above; there is no 1-million-token window, audio or built-in search, and video is handled only as separate frames; and sampling values are not optional,
since Meta recommends 1.0, 0.95 and 64 [hf-glimmer, meta-glimmer-prompting].

## What the system card reports

Meta publishes a model card (the Hugging Face page) with a trust-and-safety section and a separate methodology report, not
a system card. This is what the card says [hf-glimmer]:

- **Scope.** Meta says Glimmer is not a "Frontier AI" model under its Advanced AI Scaling Framework because it is generally
  less capable than Muse Spark, and assessed it anyway as a matter of prudence. Chemical and biological risk was rated moderate
  or lower; cyber and loss of control were inferred moderate or lower because Glimmer is broadly weaker than Muse Spark 1.0,
  which received those ratings. The card points to the Muse Spark report for the method [hf-glimmer, meta-spark-report].
- **Chemical and biological tests** (Glimmer, Gemma4-31B, Qwen3.6-27B, Kimi K3): MBCT 41.5, 50.6, 45.9, 58.9; HPCT 52.3, 54.0, 48.7,
  59.6; VCT 37.0, 43.5, 33.7, 48.0; WMDP-Bio 86.5, 85.9, 84.8, 89.1; WMDP-Chem 75.2, 80.5, 74.8, 84.2; ProtocolQA 80.2, 75.8, 69.1,
  81.9. Meta's reading: in line with its size class and below larger open-weight models, so unlikely to enable new threats.
- **Agent safety and privacy** (Glimmer, Gemma4-31B, Qwen3.6-27B): Siren AgentDojo attack success 28.4, 25.6, 40.3 (lower is
  better) with utility 94.2, 90.8, 92.7; CI Memories violation 26.4, 12.1, 53.4 (lower is better) with coverage 64.8, 53.0, 66.9. The
  model resists indirect prompt injection about as well as Gemma and better than Qwen on that test, and is worse than Gemma on
  contextual-privacy violations.
- **Four risk axes** Meta says it evaluated: content safety, agentic risk (confirming irreversible actions, minimising data,
  respecting scaffold boundaries, resisting indirect injection), privacy under contextual-integrity theory, and preparedness.
- **Training mitigations.** Safety supervised fine-tuning with agentic scenarios (tool-use limits, injection resistance,
  permission handling), safety reinforcement learning, and synthetic data on appropriate information flows.
- **Deployer advice.** The card asks deployers to test safety in context with their own datasets, to deploy inside an overall system with guardrails and to add
  human-in-the-loop confirmation for irreversible actions in agentic use. The card says the model is not intended for people under 18.
- **Not reported:** refusal and over-refusal rates, reward hacking, sycophancy, deception, sandbagging, or any cyber classifier;
  the open weights have no Meta-run safeguard layer, so refusal behaviour is whatever training left [hf-glimmer].
- The methodology report (a PDF, read in full) gives the settings behind the tables: `high` reasoning and the
  recommended sampling for Glimmer, peers in thinking mode with their own recommended settings
  [meta-glimmer-methodology].

## Behaviour observed in practice

- Speed and cost on Artificial Analysis's index: 135.9 tokens a second and 1.29 s to the first token (median of four
  hosted providers), $0.06 a task, and 59 million output tokens at `high`, which Artificial Analysis calls fairly concise;
  it also calls the hosted per-token price high for an open model of this size (class M) [aa-glimmer,
  aa-compare-glimmer].
- Low scores on long agentic work in Artificial Analysis's own tests: Terminal-Bench 4.0 1%, AutomationBench 7%, CritPt 3% (class M)
  [aa-compare-glimmer]. It is behind Muse Spark 1.2 on every index component except AA-LCR (83% against 79%).
- Hugging Face's launch blog reports day-one support in Transformers, llama.cpp, vLLM and Inference Endpoints and shows
  multimodal tool calling (class A) [hf-blog-glimmer]. No independent hands-on report of long tool-call runs was found.

## Open questions

- The maximum output length. The card is silent and the Hugging Face blog's 8,192 is an example setting.
- Whether the model makes parallel tool calls: Meta's guide and its vLLM recipe disagree.
- Quality of long tool-call runs on 4-bit builds; Meta's 0.2% and 1.0% losses are averages over 15 benchmarks.
- Refusal, over-refusal and safety behaviour of the open weights without a guardrail layer; Meta publishes none.
- Whether Meta will number later Glimmer generations.
