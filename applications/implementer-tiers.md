# Implementer tier placements

Placements are one project's inference, not a ranking of models.

Which tier of OutcomeBound's hand-off an implementer sits in, by model and effort. The three
tiers are named by what the implementer is trusted to decide: outcome, design and spec. A
placement is inferred from measured capability and recorded behaviour. One hand-off
comparison has tested the tiers so far: entry E17 of OutcomeBound's evaluation record
[ob-e17], 63 runs over three small tasks, 9 runs a cell, with one maker and one harness; the
whole gain it found was one row of one ticket. Each row holds until a further comparison or a
new release says otherwise.

This is an application of the base files: it reads each model's card at
`models/<maker>/<id>.json` (its `reasoning.levels` and `name`) and the model file beside it, and
adds a judgement for one use. The file is generated by `scripts/render.py` from
[implementer-tiers.json](implementer-tiers.json); change that file and run `make render`, never
this one. A note here matters to a hand-off only; what holds for every use of a model is in
its own file under [models/](../models/README.md).

## How a row is matched

- A row that names no effort covers every effort.
- A row that names "X and above" covers X and every effort above it, in the order of the model's
  `reasoning.levels` on its card.
- An effort below the lowest one a model's rows name takes the next tier down from that row
  (outcome to design, design to spec).
- A model with no card, a model with no row, and any quantisation below 4-bit take the spec tier
  (the default rule).
- A row holds in any harness unless its basis names one.
